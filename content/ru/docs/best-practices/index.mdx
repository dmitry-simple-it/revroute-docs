## С чего начать

Если настраиваете RevRoute с нуля:

<Steps>
  <Step title="Зафиксируйте UTM-конвенции до публикации любых ссылок">
    Переименование UTM позже расщепляет историческую статистику. Выберите схему и задокументируйте — см. [UTM-стратегию](/docs/best-practices/utm-strategy).
  </Step>
  <Step title="Выберите модель атрибуции">
    Last-click подходит для большинства партнёрских программ. First-click — только если цикл продаж длинный и важно зачислять представителя, который познакомил с брендом. См. [Атрибуцию](/docs/best-practices/attribution).
  </Step>
  <Step title="Включите правила анти-фрода при запуске, а не после">
    Бот-трафик растёт, как только партнёры начинают публично делиться ссылками. Включите rate-limit по IP и cooldown до запуска — см. [Защиту от фрода](/docs/best-practices/fraud-prevention).
  </Step>
  <Step title="Определите таксономию папок и тегов">
    Плоский workspace работает первые 100 ссылок и затем превращается в кашу. См. [Управление ссылками](/docs/best-practices/link-management).
  </Step>
</Steps>

## Общие принципы

Несколько мнений, применимых везде:

- **Один источник истины.** Не трекайте одну и ту же конверсию и через webhook → CRM, и через REST API → CRM. Выберите один путь; другой становится shadow-data, которая всегда расходится.
- **Idempotency-ключи не опциональны.** Передавайте `invoiceId` (или эквивалент) на каждом sale-событии. RevRoute использует его для дедупликации, ретрай никогда не выплатит партнёру дважды.
- **Тестируйте партнёр-side flow на staging-программе.** Создайте staging-программу, зачислите себя как партнёра и кликайте по своим ссылкам ежемесячно. Поломанные редиректы и потерянные UTM вы заметите раньше партнёров.
- **Относитесь к email-ам партнёров как к email-ам клиентов.** Партнёр, который не может залогиниться или не получает email о комиссии — оттекает мгновенно. Держите доставляемость высокой.
- **Считайте когорты по программам, не по workspace.** Агрегаты по всем программам прячут динамику каждой. Режьте по программам в отчётах.
